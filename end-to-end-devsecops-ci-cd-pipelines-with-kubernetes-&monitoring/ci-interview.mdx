# Q1. Explain your project from start to finish.

My project is an end-to-end CI pipeline for deploying a React-based Zomato Clone application using Jenkins and DevSecOps tools.

The complete flow is:

```
Developer
     │
     ▼
GitHub Repository
     │
     ▼
GitHub Webhook
     │
     ▼
Jenkins Pipeline
     │
     ├── Clean Workspace
     ├── Git Checkout
     ├── SonarQube Analysis
     ├── Quality Gate
     ├── npm install
     ├── OWASP Dependency Check
     ├── Trivy File System Scan
     ├── Docker Build
     ├── Push Image to DockerHub
     ├── Docker Scout Scan
     ├── Deploy Container
     └── Email Notification
```

Whenever a developer pushes code to GitHub, a webhook automatically triggers Jenkins.

Jenkins checks out the latest code, performs static code analysis using SonarQube, verifies the Quality Gate, installs Node.js dependencies, scans dependencies using OWASP Dependency Check, performs a filesystem scan using Trivy, builds a Docker image, pushes it to DockerHub, performs an additional image analysis using Docker Scout, deploys the application as a Docker container, and finally sends an email notification with the build status.

This pipeline ensures automation, code quality, security scanning, containerization, and deployment.

---

## Follow-up Questions

### Why did you include security scans before Docker Build?

Because if vulnerabilities are found early, we can stop the pipeline before spending time building and pushing Docker images.

This follows the Shift Left Security approach.

---

### Why deploy after Docker Scout?

Docker Scout analyzes the final Docker image.

Only after ensuring the image is acceptable do we deploy it.

# Q9. Explain your pipeline in five minutes.

## Answer

The pipeline begins when a developer pushes code to GitHub.

GitHub immediately sends a webhook request to Jenkins.

Jenkins starts the pipeline by cleaning the previous workspace.

It clones the latest application source code.

The source code is analyzed by SonarQube to detect bugs, vulnerabilities, and code smells.

The pipeline waits for the Quality Gate.

If the Quality Gate fails, the pipeline stops.

If successful, npm installs all dependencies.

OWASP Dependency Check scans all third-party libraries for known CVEs.

Trivy performs a filesystem scan to detect secrets, vulnerable packages, and configuration issues.

After all scans pass, Docker builds the application image.

The image is tagged and pushed to DockerHub.

Docker Scout analyzes the pushed image for vulnerabilities and optimization recommendations.

Finally, Jenkins deploys the Docker container and sends an HTML email with the pipeline status and attached Trivy report.

This automated workflow reduces manual effort, improves code quality, and ensures security checks are performed consistently before deployment.

# Git & GitHub Interview Questions (CI Project)

## Q11. What happens internally after `git push`?

### Answer

When I run `git push`, the following sequence happens:

1. I make changes in my local repository.
2. I stage the files using `git add .`.
3. I create a commit using `git commit -m "message"`.
4. I push the commit to the remote GitHub repository using `git push origin master`.
5. GitHub receives the new commit.
6. GitHub checks whether any Webhook is configured for that repository.
7. Since I configured a Jenkins Webhook, GitHub immediately sends an HTTP POST request to Jenkins.
8. Jenkins receives the notification and starts the pipeline.
9. Jenkins clones the latest source code from GitHub.
10. The CI pipeline begins:
    - SonarQube Analysis
    - Quality Gate
    - npm install
    - OWASP Dependency Check
    - Trivy File Scan
    - Docker Build
    - DockerHub Push
    - Docker Scout
    - Deploy Container
11. After completion Jenkins sends an email notification.

### Interview Tip

A common misconception is that GitHub directly executes Jenkins.

It does **not**.

GitHub only sends a notification.

Jenkins performs the entire build process.

## Q12. What is GitHub Webhook?

### Answer

A GitHub Webhook is an automated notification mechanism.

Whenever an event occurs in GitHub (like Push, Pull Request, Merge, Release, etc.), GitHub sends an HTTP POST request to another application.

In our project, Jenkins exposes an endpoint:

```
http://<jenkins-ip>:8080/github-webhook/
```

Whenever I push code, GitHub sends a POST request to this endpoint.

Jenkins receives the request and immediately starts the CI pipeline.

### Why is it needed?

Without Webhooks, Jenkins would never know that code has changed.

The Webhook acts as a trigger.

---

## Q13. Why did you use Webhook instead of Poll SCM?

### Answer

Both trigger Jenkins automatically, but they work differently.

### Poll SCM

- Jenkins continuously checks GitHub.
- It runs every few minutes.
- Creates unnecessary network traffic.
- Wastes CPU resources.
- Slower.

Example:

```
Every 5 minutes

Jenkins
     │
     ├── Any new code?
     │
     ├── Any new code?
     │
     ├── Any new code?
```

Even when there are no commits, Jenkins keeps checking.

---

### GitHub Webhook

GitHub itself informs Jenkins immediately after a push.

```
Developer
     │
git push
     │
GitHub
     │
HTTP POST
     │
Jenkins
```

Advantages

- Instant trigger
- Less CPU usage
- Less network traffic
- Real-time build

That's why Webhook is preferred in production.

---

## Q14. How does Jenkins know which branch to build?

### Answer

During the Git Checkout stage we specify the repository and branch.

```groovy
git branch: 'master',
    url: 'https://github.com/pray-12/DevOps-Project-Zomato-Kastro.git'
```

When Jenkins receives the Webhook, it checks out the specified branch.

If I change it to:

```groovy
branch: 'main'
```

Jenkins builds only the `main` branch.

In Multibranch Pipelines, Jenkins can automatically discover multiple branches.

## Q15. How do you secure GitHub Webhooks?

### Answer

GitHub Webhooks should never be left open.

Some common security methods are:

### 1. Secret Token

GitHub generates a secret.

Jenkins verifies the incoming request using the same secret.

If the secret doesn't match,

the request is rejected.

---

### 2. HTTPS

Webhook traffic should always use HTTPS.

This prevents attackers from intercepting requests.

---

### 3. Firewall / Security Groups

Allow only GitHub's IP ranges to access Jenkins.

Block everyone else.

---

### 4. Authentication

Only authorized repositories should trigger Jenkins.

---

### In my project

I configured:

- GitHub Webhook
- Jenkins GitHub plugin
- Security Group allowing required traffic
- Jenkins credentials for repository access

Only new deployments stop.

## Q17. What if the GitHub Webhook is not triggering?

### Answer

This is a common interview troubleshooting question.

### Step 1

Go to

GitHub

→ Settings

→ Webhooks

Check Recent Deliveries.

If the response is **200 OK**, GitHub successfully reached Jenkins.

---

### Step 2

Verify the Webhook URL.

Correct format:

```
http://<jenkins-ip>:8080/github-webhook/
```

Common mistakes:

- Missing `/github-webhook/`
- Wrong port
- Wrong IP
- Using HTTPS without SSL configured

---

### Step 3

Check Jenkins.

Ensure the **GitHub Integration** plugin is installed.

---

### Step 4

Verify Jenkins Job Configuration.

Make sure:

```
GitHub hook trigger for GITScm polling
```

is enabled.

---

### Step 5

Check the Jenkins logs.

```
Manage Jenkins

↓

System Log
```

Look for Webhook-related errors.

---

### Step 6

Verify the Security Group.

Allow inbound traffic on:

```
TCP 8080
```

---

### Step 7

Check if Jenkins is running.

```
systemctl status jenkins
```

---

### Step 8

Test the Webhook manually.

```
curl http://<jenkins-ip>:8080/github-webhook/
```

---

### Real issue I faced

Initially, my pipeline didn't trigger automatically after a push.

I checked the Webhook configuration, enabled **GitHub hook trigger for GITScm polling**, corrected the repository branch configuration, and verified that Jenkins was reachable from GitHub. After fixing those settings, the Webhook started triggering the pipeline automatically.

## Q18. Why do we have a Git Checkout stage?

### Answer

The Jenkins server does not automatically have the application's source code.

The **Git Checkout** stage downloads the latest code from GitHub into the Jenkins workspace.

Example:

```groovy
stage("Git Checkout") {
    steps {
        git branch: 'master',
            url: 'https://github.com/pray-12/DevOps-Project-Zomato-Kastro.git'
    }
}
```

After checkout, the workspace contains:

```
Dockerfile

package.json

package-lock.json

src/

public/

README.md

Jenkinsfile
```

All subsequent stages—SonarQube, npm install, OWASP Dependency Check, Trivy, Docker Build, Docker Push, and Deployment—use these files from the workspace.

Without the Git Checkout stage, Jenkins would have no source code to analyze, build, or deploy.

# Q19. Explain your Jenkinsfile line by line.

## Answer

My Jenkinsfile is written using **Declarative Pipeline syntax**, which organizes the CI pipeline into multiple stages. Each stage performs one specific task in the software delivery process.

### 1. Pipeline Declaration

```groovy
pipeline {
```

This tells Jenkins that a new pipeline is starting.

---

### 2. Agent

```groovy
agent any
```

This instructs Jenkins to run the pipeline on any available Jenkins agent (node).

---

### 3. Tools

```groovy
tools {
    jdk 'jdk21'
    nodejs 'node23'
}
```

This automatically configures the required tools before the pipeline starts.

In my project:

- JDK 21 is used for SonarScanner.
- NodeJS 23 is used to run npm commands.

---

### 4. Environment Variables

```groovy
environment {
    SCANNER_HOME = tool 'sonar-scanner'
}
```

This stores the Sonar Scanner installation path in an environment variable so it can be reused later in the pipeline.

---

### 5. Stages

```groovy
stages {
```

The pipeline is divided into multiple stages, making it easier to read, monitor, and troubleshoot.

The stages in my pipeline are:

- Clean Workspace
- Git Checkout
- SonarQube Analysis
- Quality Gate
- Install NPM Dependencies
- OWASP Dependency Check
- Trivy File System Scan
- Build Docker Image
- Push Image to DockerHub
- Docker Scout Scan
- Deploy Container

---

### 6. Clean Workspace

```groovy
cleanWs()
```

Deletes the previous build files so every build starts from a clean workspace.

---

### 7. Git Checkout

```groovy
git branch: 'master', url: 'https://github.com/pray-12/DevOps-Project-Zomato-Kastro.git'
```

Downloads the latest source code from the GitHub repository into the Jenkins workspace.

### 8. SonarQube Analysis

```groovy

    sh "$SCANNER_HOME/bin/sonar-scanner ..."
```

Runs SonarScanner to perform static code analysis and uploads the results to the SonarQube server.

### 9. Quality Gate


Waits for SonarQube to complete the analysis and checks whether the project passes the configured Quality Gate.

### 10. Install NPM Dependencies


Downloads and installs all Node.js packages defined in the `package.json` file.

---

### 11. OWASP Dependency Check

```groovy

```

Scans project dependencies for known security vulnerabilities using the OWASP Dependency Check plugin.

---

### 12. Trivy File System Scan

```groovy

```

Scans the project files for vulnerabilities, secrets, and misconfigurations and saves the report to `trivy.txt`.

### 13. Build Docker Image

```groovy
docker build -t pray12/zomato-app:latest .
```

Builds a Docker image of the application using the Dockerfile.

---

### 14. Push Image to DockerHub

```groovy
withDockerRegistry(...) {
    docker push
}
```

Authenticates with DockerHub and pushes the newly built Docker image to the DockerHub repository.

### 15. Docker Scout Scan


### 16. Deploy Container

Starts a Docker container from the image and makes the application accessible on port **3000**.

# Q30. How does Jenkins authenticate to DockerHub?

## Answer

I stored my DockerHub username and password securely in Jenkins Credentials.

In the pipeline, I used:

```groovy
withDockerRegistry(credentialsId: 'docker') {
    sh "docker push pray12/zomato-app:latest"
}
```

Internally, Jenkins performs the following steps:

1. Retrieves the DockerHub credentials from Jenkins Credentials.
2. Executes `docker login` using those credentials.
3. Authenticates with DockerHub.
4. Pushes the Docker image to the repository.

This method is secure because the credentials are encrypted and are never hardcoded in the Jenkinsfile.

# Q32. What is Static Code Analysis?

## Answer

Static Code Analysis is the process of analyzing source code **without executing the application**.

The scanner examines the code for:
- Coding mistakes
- Security issues
- Best practice violations
- Potential bugs

Since the application is not run, it is called **Static Analysis**.

# Q34. Difference between Bugs, Vulnerabilities and Code Smells?

## Answer

| Bugs | Vulnerabilities | Code Smells |
|------|-----------------|-------------|
| Coding mistakes that may cause incorrect behavior | Security weaknesses that attackers can exploit | Poor coding practices that reduce maintainability |
| Affect functionality | Affect security | Affect readability and maintainability |

# Q35. Explain Quality Gate.

## Answer

A **Quality Gate** is a set of conditions that the project must satisfy after SonarQube analysis.

Examples include:
- No Critical Bugs
- No Critical Vulnerabilities
- Maintainability Rating
- Code Coverage threshold

If all conditions are met, the Quality Gate passes; otherwise, it fails.

---

# Q36. Why is Quality Gate placed after SonarQube Analysis?

## Answer

SonarQube must first analyze the code and upload the results.

Only after the analysis is complete can Jenkins check whether the project meets the Quality Gate conditions.

So the sequence is:

```
Sonar Scan
      ↓
Upload Report
      ↓
Quality Gate
      ↓
Pass / Fail
```

---

# Q37. What happens if the Quality Gate fails?

## Answer

If the Quality Gate fails:

- Jenkins marks the stage as failed.
- The pipeline can stop (based on configuration).
- Docker image is not built.
- Deployment does not proceed.

This prevents low-quality or insecure code from reaching production.

# Q49. Why did you use OWASP Dependency Check?

## Answer

I used OWASP Dependency Check to identify **known security vulnerabilities** in third-party libraries used by my project.

It scans project dependencies against the National Vulnerability Database (NVD) and generates a vulnerability report.

---

# Q50. What does Dependency Check scan?

## Answer

It scans:

- package.json
- package-lock.json
- npm packages
- Third-party libraries

It compares their versions with known CVEs from the NVD database.

---

# Q51. Why did the first scan take around 20 minutes?

## Answer

During the first execution, OWASP Dependency Check downloaded the latest vulnerability database from the **National Vulnerability Database (NVD)**.

Since the database contains hundreds of thousands of vulnerability records, the initial download took a long time.

# Q52. Why did it become faster later?

## Answer

After the first scan, the vulnerability database was cached locally.

Subsequent scans only downloaded incremental updates, making them much faster.

---

# Q53. What is CVE?

## Answer

CVE stands for **Common Vulnerabilities and Exposures**.

Each publicly known security vulnerability is assigned a unique CVE ID, such as:

```
CVE-2025-12345
```

These IDs help identify and track security issues.

---

# Q54. What is NVD?

## Answer

NVD stands for **National Vulnerability Database**.

It is maintained by the U.S. National Institute of Standards and Technology (NIST) and contains detailed information about publicly disclosed security vulnerabilities.

OWASP Dependency Check uses this database during scans.

---

# Q55. Why use an NVD API Key?

## Answer

An NVD API Key increases the request rate limit when downloading vulnerability data.

Without an API key:
- Downloads are slower.
- Requests may be rate-limited.
- The first scan can take significantly longer.

Using an API key speeds up database updates.

---

# Q56. Why not use only SonarQube?

## Answer

SonarQube and OWASP Dependency Check serve different purposes.

- **SonarQube** analyzes the project's own source code.
- **OWASP Dependency Check** analyzes third-party libraries for known vulnerabilities.

Using both tools provides more comprehensive security coverage.

---

# Q57. What if OWASP finds a Critical vulnerability?

## Answer

If a Critical vulnerability is found:

1. Review the report.
2. Identify the affected dependency.
3. Upgrade to a secure version if available.
4. Re-run the scan.
5. If necessary, configure the pipeline to fail on Critical vulnerabilities to prevent deployment.

This ensures vulnerable dependencies are not promoted to production.

# Q94. Docker permission denied while building the image. How did you fix it?

### Answer

While building the Docker image in Jenkins, the pipeline failed with the following error:

```text
permission denied while trying to connect to the Docker daemon socket at unix:///var/run/docker.sock
```

This happened because Jenkins was running as the **jenkins** user, but that user did not have permission to access the Docker daemon.

### How I Troubleshot It

1. Read the Jenkins Console Output.
2. Noticed the error was related to `/var/run/docker.sock`.
3. Verified the Docker socket permissions.

```bash
ls -l /var/run/docker.sock
```

Output:

```bash
srw-rw---- root docker
```

Only the **root** user and members of the **docker** group could access Docker.

Next, I checked which groups Jenkins belonged to.

```bash
groups jenkins
```

Output:

```bash
jenkins : jenkins
```

The Jenkins user was **not** part of the docker group.

### Fix

Added Jenkins to the Docker group.

```bash
sudo usermod -aG docker jenkins
```

Restarted Jenkins.

```bash
sudo systemctl restart jenkins
```

Verified the group membership.

```bash
groups jenkins
```

Output:

```bash
jenkins : jenkins docker
```

After restarting Jenkins, the Docker build completed successfully.

### Interview Tip

Whenever you see **permission denied** while accessing Docker from Jenkins, first check whether the Jenkins user belongs to the Docker group.

# Q117. How would you implement rollback if a deployment fails?

## Answer

A rollback allows us to return to the last working version.

For Docker deployments, I would:

1. Tag every image with a version.

Example:

```text
pray12/zomato-app:v1
pray12/zomato-app:v2
pray12/zomato-app:v3
```

2. If deployment fails:

```bash
docker stop zomato-app
docker rm zomato-app
```

3. Start the previous stable version.

```bash
docker run -d \
--name zomato-app \
-p 3000:3000 \
pray12/zomato-app:v2
```

In Kubernetes, rollback is much easier:

```bash
kubectl rollout undo deployment/zomato-app
```

This immediately restores the previous stable version with minimal downtime.
