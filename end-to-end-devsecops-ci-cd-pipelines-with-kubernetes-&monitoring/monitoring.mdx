# Monitoring Setup — Interview Questions & Answers

Simple, conversational answers in bullet-point form — the way you'd actually explain it to an interviewer, not a textbook.

---

## Section A: Conceptual / Fundamentals

### 1. What is Prometheus?
- It's a monitoring tool that pulls metrics from your servers/apps at regular intervals.
- It stores everything as time-series data (basically, "this value at this timestamp").
- Comes with its own query language called PromQL to dig into that data.
- Works really well with Grafana for visualizing everything.

### 2. Why did you choose Prometheus?
- It's free, open-source, and has a huge community/exporter ecosystem.
- It pulls metrics itself, so I don't have to worry about apps pushing data reliably.
- If a target goes down, Prometheus notices immediately because the scrape just fails.
- Pairs perfectly with Grafana, which most teams already use.

### 3. Why not CloudWatch?
- CloudWatch is great, but it's AWS-only — if we ever move off AWS, we lose everything.
- Costs add up fast since you pay per metric/API call.
- Querying and dashboarding in CloudWatch feels limited compared to PromQL + Grafana.
- Honestly, I'd still use CloudWatch for pure AWS service metrics like RDS or Lambda — it's not either/or, just depends on the use case.

### 4. Explain Prometheus architecture (in simple terms).
- Prometheus server sits in the middle and does the scraping.
- Exporters (like Node Exporter) sit on each server exposing metrics on a specific port.
- Prometheus scrapes those exporters on a timer and saves the data locally (TSDB).
- Grafana then connects to Prometheus to show all that data as nice dashboards.
- Optionally, Alertmanager sits alongside to fire off alerts when something's wrong.

### 5. What are Targets?
- A target is just one specific endpoint Prometheus is scraping.
- Basically an IP + port combo, like `10.0.1.5:9100`.
- You can see all your targets and whether they're healthy under Status → Targets in the UI.

### 6. What are Jobs?
- A job is just a group of similar targets under one name.
- Example: I named the group `node_exporter` — if I add 5 more servers running Node Exporter, they all fall under that same job.
- Makes it easy to filter/query later, like "show me all node_exporter targets that are down."

### 7. What is Scraping?
- It's just Prometheus hitting a URL like `http://server:9100/metrics` every X seconds.
- It reads whatever text comes back and stores it with a timestamp.
- That's really the entire "collection" mechanism — no agents pushing data, Prometheus does all the pulling.

### 8. What is `prometheus.yml`?
- It's the main config file for Prometheus, sitting at `/etc/prometheus/prometheus.yml`.
- This is where you tell Prometheus what to scrape — all the jobs and targets go here.
- Also has global settings like how often to scrape by default.
- If you mess up this file, your new targets won't show up, so it's important to validate it before reloading.

### 9. Why use systemd service (instead of just running the binary manually)?
- If I just run the Prometheus binary in a terminal, it dies the moment I close the SSH session.
- systemd keeps it running in the background permanently.
- If the server reboots, systemd auto-starts it again — I don't have to remember to do it manually.
- Also gives auto-restart if it crashes, which is huge for something that's supposed to always be watching.

### 10. Why port 9090?
- That's just Prometheus's default port — nothing magical about it.
- Everyone in the community knows "9090 = Prometheus," so it's more of a convention.
- You could run it on any other free port if you wanted, just change the flag.

### 11. What is TSDB?
- Stands for Time Series Database — it's how Prometheus stores its data internally.
- Every metric gets saved with a timestamp, so you can go back and see how a value changed over time.
- Lives in the `/data` folder in our setup.
- Grows over time, so disk space is something you have to keep an eye on.

### 12. Why `promtool check config`?
- It's a quick sanity check on your `prometheus.yml` before you actually reload it.
- Catches YAML mistakes — wrong indentation, missing colons, that kind of thing.
- Way better to catch a typo here than to reload and wonder why your new job isn't showing up.
- If it says "SUCCESS," you're good to go.

### 13. Why `curl -X POST /-/reload`?
- This tells Prometheus to re-read its config file without restarting the whole service.
- Saves you from any gap in monitoring — if you restart Prometheus fully, you lose a few seconds/minutes of scraping.
- Super handy when you're just adding a new job and don't want downtime.

### 14. Why `--web.enable-lifecycle`?
- This flag is what actually allows that reload endpoint to work.
- Without it, hitting `/-/reload` just gets rejected.
- Basically it's the switch that turns on "management via API" for Prometheus.

## Section B: Node Exporter

### 15. What is Node Exporter?
- It's a small agent you install on a server to expose system-level stats.
- Things like CPU usage, memory, disk space, network traffic.
- Prometheus then scrapes this agent to pull all that info in.

### 16. Why do we need Node Exporter?
- Prometheus by itself doesn't know anything about a server's hardware — it needs something local on that machine to report it.
- Node Exporter is that "reporter" — it just sits there and answers "here's what's going on with this machine" whenever asked.

### 17. What metrics does it expose?
- CPU usage (per core, per mode — idle, user, system).
- Memory and swap usage.
- Disk space and disk I/O.
- Network traffic in/out.
- Basically anything OS-level you'd normally check with `top`, `df`, or `free`.

### 18. Why port 9100?
- Same story as Prometheus's 9090 — it's just the default port everyone agreed on.
- Lets multiple exporters run on the same box without stepping on each other (MySQL exporter uses 9104, for example).
- You can change it, but there's rarely a reason to.

### 19. What is `/metrics`?
- It's the actual URL path where the exporter dumps out all its data.
- If you open `http://server:9100/metrics` in a browser, you'll see plain text — lines like `node_cpu_seconds_total{...} 12345`.
- That raw text is exactly what Prometheus reads when it scrapes.

### 20. Why run Node Exporter as a separate user?
- Same reasoning as Prometheus — don't run things as root if you don't have to.
- If someone exploits a bug in Node Exporter, they're stuck with a limited, no-login user instead of full root access.
- It's a small extra step that adds real security value.

### 21. Why systemd (for Node Exporter too)?
- Same reason as Prometheus — keeps it running in the background, restarts it on crash, and auto-starts on reboot.
- Without it, you'd have to babysit the process manually every time the server restarts.

### 22. How does Prometheus collect metrics from Node Exporter?
- I add a job in `prometheus.yml` pointing to `<server-ip>:9100`.
- Prometheus scrapes that URL every 15 seconds (or whatever interval is set).
- The data gets stored in Prometheus's TSDB, and from there Grafana can visualize it.

## Section C: Grafana

### 23. What is Grafana?
- It's the visualization tool — takes data from Prometheus and turns it into actual readable dashboards.
- Graphs, gauges, tables, whatever you need.
- Can also set up alerts and connect to more than just Prometheus if needed.

### 24. Why Grafana if Prometheus already has graphs?
- Prometheus's built-in graphs are really just for quick debugging, not something you'd show to a team.
- Grafana lets you save dashboards, share them, set up proper alerting, and make things look actually presentable.
- It's the difference between a scratchpad and a proper dashboard tool.

### 25. Why add Prometheus as a Data Source?
- Grafana doesn't collect any data on its own — it just visualizes data from somewhere else.
- So you have to tell it "hey, go pull your numbers from this Prometheus URL."
- Once that connection is set (and tested), Grafana can start building charts off Prometheus's data.

### 26. Explain Dashboard.
- Think of a dashboard as one page/screen made up of multiple graphs (panels).
- Example: a "Server Health" dashboard might have CPU, memory, disk, and network panels all on one screen.
- You can save it, share it with the team, and come back to it anytime.

### 27. Explain Panels.
- A panel is just one individual chart or visualization inside a dashboard.
- Could be a line graph, a gauge, a table — whatever fits the metric.
- Each panel runs its own PromQL query behind the scenes to pull the exact data it needs.

### 28. Why import Dashboard ID 1860?
- No point building a Node Exporter dashboard from scratch when the community already made an amazing one.
- 1860 is basically the "gold standard" Node Exporter dashboard everyone uses — has CPU, memory, disk, network, all pre-built.
- Saved a ton of time — just paste the ID, pick Prometheus as the source, and it's ready.

### 29. How did you monitor Jenkins?
- Installed the Prometheus plugin on Jenkins, which exposes metrics at `/prometheus` (not the usual `/metrics`).
- Added a job in `prometheus.yml` pointing to Jenkins's IP and port, with that custom path.
- Then imported a Jenkins-specific Grafana dashboard (ID 9964) to visualize build health, job stats, etc.

### 30. Why use Grafana in production?
- Teams need something they can actually check every day, not a raw query tool.
- Grafana gives history, alerting, and a shared view everyone can look at — ops, devs, managers.
- It also supports multiple data sources, so as the stack grows (logs, other databases), it can all live in one place.

## Section D: Troubleshooting

### 31. Prometheus service won't start.
- **Symptoms:** `systemctl status prometheus` shows failed/inactive.
- **Root cause:** usually a bad config file, wrong file permissions on `/data` or `/etc/prometheus`, or the port already in use.
- **Commands:** `journalctl -u prometheus -n 50` to see the actual error, `promtool check config` to rule out a YAML issue.
- **Fix:** correct the config, fix ownership with `chown -R prometheus:prometheus /data /etc/prometheus`, then `systemctl daemon-reload` and restart.

### 32. Node Exporter target is DOWN.
- **Symptoms:** Prometheus UI shows the node_exporter target as DOWN, no data in Grafana.
- **Root cause:** service isn't running, port 9100 isn't open in the security group, or it's bound to localhost only.
- **Commands:** `systemctl status node_exporter`, `curl http://localhost:9100/metrics` on that server itself, `curl http://<ip>:9100/metrics` from the Prometheus server.
- **Fix:** start the service if it's down, open the port in the security group, or fix the listen address.

### 33. Jenkins target is DOWN.
- **Symptoms:** Jenkins job shows DOWN in Prometheus targets.
- **Root cause:** wrong metrics path (forgot `/prometheus` instead of default `/metrics`), Jenkins itself is down, or plugin isn't installed/enabled.
- **Commands:** open `http://<jenkins-ip>:8080/prometheus` directly in a browser to see if it responds.
- **Fix:** correct the `metrics_path` in the job config, or fix/restart Jenkins if it's actually down.

### 34. Grafana cannot connect to Prometheus.
- **Symptoms:** "Save & Test" fails with an error when adding the data source.
- **Root cause:** wrong URL, trailing slash causing a bad path, or a firewall blocking Grafana from reaching Prometheus's port.
- **Commands:** from the Grafana server, `curl http://<prometheus-ip>:9090/api/v1/status/config` to test connectivity manually.
- **Fix:** correct the URL, remove trailing slash, open the right port if it's blocked.

### 35. Dashboard shows "No Data."
- **Symptoms:** panels are empty even though targets show UP.
- **Root cause:** wrong data source picked on the panel, metric name doesn't match (version differences), or the selected time range in Grafana doesn't overlap with when data was collected.
- **Commands:** run the exact same PromQL query directly in Prometheus's UI to see if data even exists there.
- **Fix:** fix the data source/query in the panel, or widen the time range.

## Section E: Scenario-Based Questions

### 36. CPU suddenly reaches 100%. How would you investigate?
- Spot it first on the Node Exporter Grafana dashboard — CPU panel spikes.
- Break the CPU metric down by mode (user/system/iowait) — helps tell if it's an actual process hogging CPU or a disk-related issue.
- Check if anything else lines up with that time — a deploy, a cron job, a Jenkins build.
- SSH in and run `top` to catch the actual process live, since Node Exporter only gives system-wide numbers, not per-process.
- Afterward, maybe add an alert so next time it pages someone instead of being found manually.

### 37. Node Exporter stops exposing metrics.
- Check if the service is even running — `systemctl status node_exporter`.
- If it's running but not showing data, hit `curl localhost:9100/metrics` directly on that box.
- Could be a permissions issue, a crashed process that systemd hasn't restarted yet, or it silently died — check logs with `journalctl -u node_exporter`.
- Restart the service and confirm Prometheus picks it back up under Targets.

### 38. Prometheus storage becomes full.
- First thing — check how much data retention is set to (`--storage.tsdb.retention.time`), default is 15 days.
- If disk keeps filling, either reduce retention, reduce scrape frequency, or just give it a bigger disk.
- Longer-term fix: don't rely on local storage at all — send data to something like Thanos or VictoriaMetrics for long-term storage instead of keeping everything on one disk.

### 39. Grafana dashboards are blank.
- Same as the "No Data" troubleshooting case — check the data source connection first.
- If the data source is fine, check individual panel queries — sometimes just one panel breaks due to a metric rename.
- Also double check the dashboard's time range picker at the top — easy to miss that it's set to a weird window.

### 40. Jenkins server goes down. How do you confirm it from Prometheus?
- Don't even need to log into Jenkins — just check Prometheus directly.
- Query `up{job="jenkins"}` — if it returns 0, Prometheus can't reach it.
- Go to Status → Targets and look at the actual error message for that job — tells you if it's a timeout, connection refused, etc.
- That error usually tells you whether it's Jenkins itself crashing, the whole server being down, or just a network/security-group block.

## Section F: Extra Ones Worth Knowing

### 41. What is `metrics_path` and why did we need it for Jenkins?
- By default, Prometheus assumes metrics live at `/metrics`.
- Jenkins's Prometheus plugin exposes them at `/prometheus` instead.
- So without explicitly setting `metrics_path: '/prometheus'` in the job, Prometheus would hit the wrong URL and get a 404.

### 42. What's the difference between Restart=on-failure and Restart=always in systemd?
- `on-failure` — only restarts if the service actually crashes or errors out.
- `always` — restarts no matter how it stopped, even if someone intentionally stopped it cleanly.
- For something like Prometheus, `on-failure` makes more sense so you're not fighting systemd during planned maintenance.

### 43. What happens if you edit the systemd service file but forget `daemon-reload`?
- Your changes just won't take effect, even if you restart the service.
- systemd caches the unit files in memory, so it needs `daemon-reload` to actually re-read the file from disk.
- Classic "why isn't my change working" moment for beginners.

### 44. What's the security concern with leaving Prometheus/Grafana ports open to the whole internet?
- Anyone could scan and access your metrics/dashboards, which can leak internal info.
- Better approach — only allow Prometheus/Node Exporter ports from the monitoring server's own IP/security group, not `0.0.0.0/0`.
- Grafana can stay a bit more open if it's behind a login, but ideally locked to internal IPs or VPN too.

### 45. If leadership wants 6 months of historical data but retention is only 15 days, what do you say?
- Explain that Prometheus's local storage isn't built for long-term data — it's meant to be lightweight and fast.
- Options: bump up the retention setting if disk allows, or better, plug in a remote storage system like Thanos/Cortex/VictoriaMetrics that's actually designed for long-term retention.
