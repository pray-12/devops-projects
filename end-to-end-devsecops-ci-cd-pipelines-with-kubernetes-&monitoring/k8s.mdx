# Amazon EKS Cluster Setup Interview Questions (Q1–Q8)

---

# Q1. Why did you choose Amazon EKS for your project?

## Answer

I chose **Amazon EKS (Elastic Kubernetes Service)** because it is a **managed Kubernetes service** provided by AWS. Instead of setting up and managing the Kubernetes control plane myself, AWS manages it automatically.

For my project, I already had the application running in Docker containers. The next step was to deploy it on Kubernetes for better scalability and availability. Since the project was hosted on AWS, EKS was the most suitable choice.

### Why EKS?

- Managed Kubernetes service
- High Availability Control Plane
- Automatic upgrades and patching
- Integration with AWS services
- Easier cluster management
- Production-ready

### In my project

My CI pipeline pushed Docker images to DockerHub. ArgoCD then deployed those images into my Amazon EKS cluster.

---

# Q2. Why do we need kubectl, eksctl, and AWS CLI?

## Answer

All three tools have different responsibilities.

### kubectl

**What?**

The Kubernetes command-line tool.

**Why?**

It communicates with the Kubernetes API Server to manage cluster resources.

Examples:

```bash
kubectl get nodes
kubectl get pods
kubectl apply -f deployment.yaml
kubectl delete pod <pod-name>
```

---

### eksctl

**What?**

A CLI tool specifically designed to create and manage EKS clusters.

**Why?**

Without eksctl, we would need to manually create:

- VPC
- IAM Roles
- Security Groups
- EKS Cluster
- Node Groups
- CloudFormation Stacks

eksctl automates all these steps.

Example:

```bash
eksctl create cluster --name=kastrocluster
```

---

### AWS CLI

**What?**

Command-line tool to communicate with AWS services.

**Why?**

Used for authentication and managing AWS resources.

Example:

```bash
aws configure
```

It stores:

- Access Key
- Secret Key
- Region
- Output Format

---

### Interview Tip

A common interview question is:

**Why can't we create an EKS cluster using only kubectl?**

Answer:

Because **kubectl only manages Kubernetes resources after a cluster exists.** It cannot create AWS infrastructure like VPCs, IAM roles, or EC2 instances. That is handled by `eksctl` or the AWS Console.

---

# Q3. What happens during `aws configure`?

## Answer

`aws configure` connects your local machine to your AWS account.

Command:

```bash
aws configure
```

It asks for:

```
AWS Access Key ID
AWS Secret Access Key
Default Region
Output Format
```

Example:

```
AWS Access Key ID : ****************
AWS Secret Access Key : ****************
Region : ap-south-1
Output : json
```

These values are stored locally under:

```
~/.aws/credentials
~/.aws/config
```

After configuration, tools like:

- AWS CLI
- eksctl
- Terraform

can authenticate with AWS automatically.

---

### Why is it required?

Without AWS credentials:

- EKS cluster creation fails
- EC2 creation fails
- IAM creation fails

because AWS doesn't know who is making the request.

Command:

```bash

--name=kastrocluster \
--region=ap-northeast-1 \
--zones=ap-northeast-1a,ap-northeast-1c \
--without-nodegroup
```

---

### --name

Specifies the cluster name.

```
kastrocluster
```

AWS creates an EKS cluster with this name.

---

### --region

Specifies where the cluster will be created.

Example:

```
ap-northeast-1
```

This means Tokyo Region.

---

### --zones

Specifies Availability Zones.

Example:

```
ap-northeast-1a
ap-northeast-1c
```

Using multiple AZs improves High Availability.

---

### --without-nodegroup

Because it gives more flexibility.

- desired instance type

Because my application required Kubernetes features such as Deployments, Services, Ingress, ArgoCD, and Helm.

No.

# Q9. What is an IAM OIDC Provider?

## Answer

An **IAM OIDC (OpenID Connect) Provider** establishes a trust relationship between your **Amazon EKS cluster** and **AWS IAM**.

Normally, Kubernetes Service Accounts are only recognized inside the Kubernetes cluster. AWS IAM has no knowledge of these accounts.

By associating an OIDC provider, AWS can trust identities coming from Kubernetes, allowing Pods to securely access AWS services without embedding AWS credentials.

### Why is it needed?

Without an OIDC provider:

- Pods cannot assume IAM Roles.
- Applications would need hardcoded AWS Access Keys (which is insecure).

With OIDC:

- Pods can securely obtain temporary AWS credentials.
- No secrets need to be stored inside containers.

---

### Command

```bash
eksctl utils associate-iam-oidc-provider \
--region ap-northeast-1 \
--cluster kastrocluster \
--approve
```

---

### In my project

I associated the OIDC provider immediately after creating the EKS cluster so that Kubernetes workloads could later use IAM Roles if they needed access to AWS services.

---

# Q10. Why do we associate an IAM OIDC Provider?

## Answer

We associate an IAM OIDC Provider so that Kubernetes Service Accounts can securely authenticate with AWS IAM.

This enables **IAM Roles for Service Accounts (IRSA)**.

### Without OIDC

```
Pod
 ↓
Needs AWS S3

No authentication available

Access Denied
```

---

### With OIDC

```
Pod
↓

Service Account
↓

OIDC Provider
↓

IAM Role
↓

AWS Services
```

The Pod receives temporary credentials instead of long-term AWS Access Keys.

---

### Benefits

- Improved security
- Temporary credentials
- No hardcoded secrets
- Fine-grained permissions
- AWS best practice

---

# Q11. What is IAM Roles for Service Accounts (IRSA)?

## Answer

IRSA allows a Kubernetes Service Account to assume a specific AWS IAM Role.

Instead of giving every worker node broad permissions, you assign only the required permissions to individual Pods.

### Example

Suppose your application needs to access:

- Amazon S3
- DynamoDB

Instead of attaching those permissions to the EC2 node, you create:

```
Service Account
↓

IAM Role

↓

S3 Read Access
```

Only Pods using that Service Account receive the permissions.

---

### Why use IRSA?

- Least privilege principle
- Better security
- No AWS keys inside Pods
- Temporary credentials
- Easier auditing

---

### Interview Tip

A common question is:

**Can multiple Pods use different IAM Roles?**

Yes.

Each Pod can use a different Kubernetes Service Account, and each Service Account can be mapped to a different IAM Role.

# Q16. How do worker nodes join the EKS cluster?

## Answer

After the Node Group is created, each EC2 instance automatically joins the cluster.

The process is:

```
EC2 Instance Starts
        ↓
Bootstrap Script Runs
        ↓
kubelet Starts
        ↓
Authenticates with EKS Control Plane
        ↓
Registers as a Worker Node
        ↓
Status becomes Ready
```

You can verify this using:

```bash
kubectl get nodes
```

Example:

```
NAME                                   STATUS
ip-192-168-29-199                      Ready
ip-192-168-46-71                       Ready
```

Once the nodes are in the **Ready** state, Kubernetes can schedule Pods on them.

# Common Troubleshooting Questions

## Worker nodes are not joining the cluster. What would you check?

- Verify the Node Group was created successfully.
- Check the EC2 instances are running.
- Ensure the IAM Role is attached correctly.
- Verify Security Groups allow communication with the control plane.
- Check subnet configuration.
- Review the bootstrap logs on the EC2 instance.

---

## Why is the node status `NotReady`?

Possible causes include:

- kubelet service is not running.
- Networking issues.
- CNI plugin failure.
- Resource constraints.
- IAM or authentication problems.

---

## What happens if one worker node fails?

Kubernetes detects the failure and reschedules Pods onto healthy worker nodes, provided sufficient capacity exists.

---

## Can we increase the number of worker nodes later?

Yes.

You can:

- Update the Auto Scaling Group size.
- Use `eksctl scale nodegroup`.
- Configure the Cluster Autoscaler for automatic scaling.

---

# Interview Tips

- Clearly distinguish the **Control Plane** (managed by AWS) from **Worker Nodes** (where Pods run).
- Understand why **OIDC** is required before **IRSA** can be used.
- Be able to explain every important flag in the `eksctl create nodegroup` command.
- Know that **Managed Node Groups** reduce maintenance compared to self-managed nodes.
- Mention security best practices such as using **temporary IAM credentials through IRSA instead of storing AWS Access Keys in Pods**.

# Q1. What is GitOps?

## Answer

GitOps is a deployment methodology where Git acts as the **single source of truth** for Kubernetes deployments.

Instead of manually running deployment commands like:

```bash
kubectl apply -f deployment.yaml
```

we store all Kubernetes manifests inside a Git repository.

ArgoCD continuously monitors that repository.

Whenever a change is committed, ArgoCD automatically synchronizes the Kubernetes cluster with Git.

---

### Traditional Deployment

```
Developer
     ↓
kubectl apply
     ↓
Kubernetes
```

Deployment depends on engineers manually applying YAML files.

---

### GitOps Deployment

```
Developer
      ↓
GitHub Repository
      ↓
ArgoCD
      ↓
Kubernetes Cluster
```

Git becomes the desired state of the cluster.

---

### In my project

After Jenkins completed the CI pipeline:

- Source code was built.
- Docker image was created.
- Docker image was pushed to DockerHub.

The CD part started here.

ArgoCD watched my Kubernetes repository.

When I updated the deployment.yaml image tag, ArgoCD detected the change and deployed the new version automatically.

---

# Q8. Why is ArgoCD called Declarative?

## Answer

In declarative deployment we describe:

"What the cluster should look like."

Example:

```yaml
replicas: 2

image: pray12/zomato-app:latest
```

We never tell Kubernetes HOW to create Pods.

We only define the desired state.

ArgoCD ensures the cluster always matches this desired state.

---

# Q9. What is Drift Detection?

## Answer

Drift means:

Actual cluster configuration differs from Git.

Example:

Git:

```
replicas: 2
```

Someone manually scales:

```
kubectl scale deployment zomato --replicas=5
```

Now:

Git

```
2 replicas
```

Cluster

```
5 replicas
```

ArgoCD detects this difference.

If Auto Sync is enabled,

ArgoCD changes the cluster back to 2 replicas.

# Q27. Why create a separate namespace for Node Exporter?

## Answer

Namespaces logically separate applications inside Kubernetes.

Instead of deploying everything into the **default namespace**, it's considered best practice to isolate monitoring components.

---

### Example

```
default

├── Zomato Pods
├── Services
└── Deployments
```

Monitoring components mixed with application resources become difficult to manage.

---

Better approach:

```
default
│
├── Application

argocd
│
├── ArgoCD Components

prometheus-node-exporter
│
├── Node Exporter Pods
```

---

### Benefits

- Better organization
- Easier troubleshooting
- Easier RBAC management
- Cleaner resource separation
- Safer deletion

---

### Command Used

```bash
kubectl create namespace prometheus-node-exporter
```

---

### Interview Tip

Namespaces do **not** provide complete security.

They provide **logical isolation**, while security is enforced using RBAC and Network Policies.

```yaml
- job_name: 'k8s'
  metrics_path: /metrics
  static_configs:
    - targets:
      - '<NodePublicIP>:9100'
```

Reloaded Prometheus.

Node metrics immediately became available.

# Q29. How does Prometheus scrape node metrics?

## Answer

Prometheus follows a **pull model**.

It periodically sends HTTP requests to Node Exporter.

---

Flow:

```
Prometheus

↓

GET /metrics

↓

Node Exporter

↓

Returns Metrics

↓

Prometheus Stores Metrics
```

---

Example response:

```
node_cpu_seconds_total

node_memory_MemAvailable_bytes

node_network_receive_bytes_total

node_filesystem_avail_bytes
```

Thousands of metrics are returned.

---

Prometheus stores these values inside its Time Series Database (TSDB).

---

### Why Pull Instead of Push?

Advantages:

- Simpler architecture
- Easier service discovery
- Better scalability
- No agents need to push data

---

### Interview Tip

Follow-up question:

**Can Prometheus receive pushed metrics?**

Yes.

Using **Pushgateway**.

It is mainly used for short-lived batch jobs.

Node Exporter always uses the pull model.

# Q30. Why does Node Exporter use port 9100?

## Answer

9100 is the default HTTP port exposed by Node Exporter.

When installed, Node Exporter starts an HTTP server.

```
Node Exporter

↓

http://NodeIP:9100/metrics
```

Prometheus accesses this endpoint to collect metrics.

---

Example:

```bash
curl http://3.110.xxx.xxx:9100/metrics
```

Returns:

```
node_cpu_seconds_total

node_memory_MemAvailable_bytes

node_load1
```

---

### In My Project

I opened port **9100** in the EC2 Security Group so Prometheus running on the monitoring server could access the metrics endpoint.

If this port is blocked:

```
Prometheus

↓

Connection Refused

↓

Target DOWN
```

# Q31. Why reload Prometheus instead of restarting it?

## Answer

After modifying **prometheus.yml**, Prometheus must reload the configuration.

Instead of restarting the service, we used:

```bash
curl -X POST http://localhost:9090/-/reload
```

---

### Why reload?

- No downtime
- Existing metrics remain available
- Faster than restarting
- Configuration changes are applied immediately

---

### Restart

```
Prometheus

↓

Stops

↓

Starts Again

↓

Temporary Monitoring Gap
```

---

### Reload

```
Prometheus

↓

Reads Updated Configuration

↓

Continues Running
```

---

### Why did this work?

Because Prometheus was started with:

```bash
--web.enable-lifecycle
```

This enables the reload API.

Without it, the reload request would fail.

# Q33. ArgoCD shows **OutOfSync**. How would you troubleshoot and fix it?

## Answer

OutOfSync means the **desired state in Git** is different from the **actual state running in the Kubernetes cluster**.

It doesn't necessarily mean something is broken—it simply means the cluster doesn't match Git.

---

### Example

Git Repository

```
Replicas: 2

Image:
pray12/zomato-app:v2
```

Cluster

```
Replicas: 3

Image:
pray12/zomato-app:v1
```

ArgoCD compares both states and reports:

```
OutOfSync
```

---

## Troubleshooting Steps

### Step 1

Check the application status.

```bash
kubectl get applications -n argocd
```

or through the ArgoCD UI.

---

### Step 2

Open the application in ArgoCD.

It highlights exactly which resources differ.

For example:

```
Deployment

↓

Image differs
```

or

```
Replicas differ
```

---

### Step 3

Check Git.

Verify:

- deployment.yaml
- service.yaml
- ingress.yaml

Make sure the latest commit contains the expected configuration.

---

### Step 4

Check whether someone manually modified the cluster.

For example:

```bash
kubectl scale deployment zomato --replicas=5
```

This causes configuration drift.

---

### Step 5

Synchronize the application.

Either:

```
ArgoCD UI

↓

SYNC
```

or

```bash
argocd app sync zomato
```

---

### Root Causes

- Manual kubectl changes
- Git repository updated
- Failed synchronization
- Wrong image tag
- Deleted resources

---

### Interview Tip

**OutOfSync** means:

> Git and Kubernetes are different.

It does **not** always mean the application is unhealthy.
